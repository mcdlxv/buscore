# Дизайн: AI-контроль безопасности автобусного парка — v1

- **Дата:** 2026-08-13
- **Статус:** одобрен владельцем продукта (все 4 секции)
- **Разработка:** AI-ассистенты (Claude Code / Codex), владелец — оператор и продакт
- **Исходная идея:** Obsidian, `Ideas/2026-08-13 — AI-контроль безопасности автобусного парка.md`

## 1. Контекст и цель

Целевой сценарий — городской парк электробусов (несколько десятков бортов), работающий
~05:00–22:00. Видео с бортовых камер уже выводится в диспетчерскую в реальном времени,
но смотреть его некому: уследить за каждым автобусом вручную невозможно.

Продукт — софт по подписке: AI непрерывно следит за телеметрией и видео, а сотрудник
службы безопасности (СБ) разбирает только готовые события с видеодоказательствами.
AI не принимает дисциплинарных решений — только находит и показывает.

**Цель пилота (выбор владельца): живая лента событий** — работающая в реальном времени
лента с клипами и кнопками «Подтвердить / Отклонить».

Проверенные факты (первоисточники Yutong, проверено 2026-08-13):

- Link+ Basic-E (второй снизу тариф) включает **open data interface**; событийная
  подписка (~28 типов: превышение скорости, резкие манёвры, простой, «двери открыты
  на холостом ходу» и др.); история координат/скорости выгружается. Источник: PDF
  Link+ (май 2025, сентябрь 2025).
- Существует казахстанское облако Link+: `kziov.vehicleplus.net`.
- E12 PRO (региональная спецификация): видеонаблюдение 1080p — стандарт; подсчёт
  пассажиров на 3 дверях — стандарт; DDAW (контроль усталости) — опция.
- Комплектация бортов конкретного парка уточняется на этапе пилота.

## 2. Журнал решений

| Решение | Обоснование |
| --- | --- |
| Цель пилота — живая лента, не батч-отчёт | Выбор владельца; эффектнее для продажи |
| Объём v1: телеметрия-пакет + телефон + курение/сонливость | Салонные события (падение/драка) — в backlog: исследовательский уровень точности |
| Архитектура: один сервис (вариант A) | Минимум движущихся частей для соло-оператора и AI-разработки |
| Без n8n | Ядро — stateful-логика, CV и UI, которые n8n не закрывает; добавим на «краях», если появятся интеграционные задачи. Проверить лицензию Sustainable Use, если станет частью продаваемого сервиса |
| Стек «скучный»: FastAPI, PostgreSQL+PostGIS, Docker | Максимальная надёжность генерации кода AI-ассистентами |
| Панель server-rendered: Jinja2 + HTMX + SSE, Leaflet | Без сборки фронтенда; живые обновления через SSE |
| Vision по сэмплам 1–2 кадра/сек | Телефон/курение/сон — длящиеся состояния; экономия GPU и трафика на порядок |
| Пилот без GPU | 1 борт на 1–2 к/с тянет CPU; GPU — при масштабировании |
| Replay — равноправный источник данных | Демо/разработка/тесты не ждут доступов парка |
| Хостинг: Docker на VPS в РК или сервере парка | Решится политикой данных парка; переезд без переделки |

## 3. Архитектура

Один репозиторий, один деплой (Docker Compose), модули:

```text
Источники: Link+ API | Видеоплатформа парка | Replay (записи как живые)
     │
     ▼
bus-core (FastAPI):
  ingest/   — опрос Link+ API; replay-проигрыватель
  rules/    — телеметрические детекторы (стейт-машины на борт)
  vision/   — CV: телефон, курение, сонливость (YOLO + MediaPipe)
  clips/    — запрос видеофрагмента к событию (адаптер под платформу парка)
  feed/     — API панели + SSE-поток ленты
  notify/   — Telegram-уведомления
     │
     ▼
PostgreSQL + PostGIS  +  файловое хранилище клипов
     │
     ▼
Живая лента (веб-панель СБ)  +  Telegram
     │
     ▼
Сотрудник СБ: Подтвердить / Отклонить ──► вердикты в БД ──► отчёты, рейтинги, тюнинг порогов
```

- Адаптер `clips/` дописывается, когда станет известен вендор видеоплатформы парка.
  До этого клипы поставляет replay-источник.
- `vision/` — отдельный контейнер-воркер; при недоступности живого потока работает по
  записям за ночь (лента получает DMS-события с задержкой — деградация, не отказ).

## 4. Каталог событий v1

Все пороги — значения по умолчанию, редактируются в `rule_configs` без передеплоя.

| Тип | Правило (по умолчанию) | Источник |
| --- | --- | --- |
| `speeding` | скорость > лимита маршрута +10 км/ч дольше 10 с | rules |
| `harsh_brake` / `harsh_accel` | события Link+; fallback — производная скорости | rules |
| `route_deviation` | дальше 200 м от полилинии маршрута дольше 2 мин | rules |
| `stop_skip` | вход в геозону обязательной остановки → скорость не опустилась ниже 5 км/ч **и** двери не открылись → выход | rules |
| `long_idle` | скорость ≈ 0 вне геозон остановок/депо дольше 5 мин | rules |
| `phone_use` | состояние «телефон» ≥ 15 с по сэмплам | vision |
| `smoking` | состояние «курение» ≥ 10 с | vision |
| `drowsiness` | PERCLOS/зевота/кивки в окне 60 с; при наличии штатного DDAW — берём его события отдельным источником, свой детектор не дублируем | vision / DDAW |

Backlog (вне v1): падение пассажира, драка, подсчёт пассажиропотока в аналитике.

## 5. Жизненный цикл события

`candidate` (rules/vision, с confidence) → фильтры: дедупликация, кулдаун (борт+тип),
дневной бюджет тревог (цель ≤ 30/день на парк, настраивается) → `published` (SSE в ленту +
Telegram) → вердикт СБ: `confirmed` | `rejected` с обязательной причиной («ложное
срабатывание» / «не нарушение» / «дубль») → отчёты и рейтинг водителей.

Причины отклонений — датасет для еженедельного тюнинга порогов: смотрим худший по
ложным срабатываниям тип и правим его конфиг.

## 6. Модель данных

- `buses` — борт, госномер, идентификатор в Link+
- `drivers`, `shifts` — водители и смены (v1: ручной ввод / CSV-импорт графика)
- `routes` (полилиния, лимит скорости маршрута — v1: один лимит на маршрут), `stops`
  (точка, радиус геозоны, обязательность), `route_stops`
- `signals` — сырая телеметрия; партиции по дням; ретеншн 90 дней
- `events` — тип, статус, время начала/конца (UTC сервера + исходное время источника),
  гео, борт, водитель, смена, confidence, clip_id, вердикт (кто/когда/причина)
- `clips` — файл, длительность, привязка к событию, срок хранения
- `rule_configs` — пороги правил с историей изменений
- `users` — роли: админ, СБ (лента+вердикты), руководство (read-only отчёты)

## 7. UI: живая лента

- Карточка события: тип, борт, маршрут, водитель, время, длительность, confidence,
  клип (автостарт за 5 с до нарушения), мини-карта (Leaflet) по клику, кнопки
  «Подтвердить» / «Отклонить» с горячими клавишами `1`/`2`.
- Карточка публикуется мгновенно по телеметрии; клип догружается асинхронно
  (статус «клип запрошен…», затем «клип недоступен» после исчерпания ретраев).
- Шапка: статистика дня (события / ждут разбора / подтверждено / отклонено), фильтры
  (новые / все за смену / подтверждённые), индикатор live.
- Вкладка «Отчёт»: неделя/месяц, разрезы по водителям/маршрутам/типам, экспорт CSV.
- Адаптивная вёрстка; мобильный канал v1 — Telegram. Отдельного приложения нет (YAGNI).
- Целевая скорость разбора: ≤ 30 секунд на событие.

## 8. Уведомления

- Telegram по ролям: СБ — все типы; директор — выбранные (настройка per-user).
- Сообщение: тип, борт, маршрут, время, ссылка на карточку.
- Тихие часы по расписанию; при превышении дневного бюджета — одна сводка вместо потока.

## 9. Надёжность и обработка ошибок

- Разрыв данных от борта: статус «нет связи» в панели; после восстановления — догрузка
  трека из истории Link+ и ретроспективный прогон детекторов; события помечаются
  «получено с задержкой».
- Клипы: ретраи с экспоненциальной паузой; лента не блокируется видео.
- Часы: два времени у события (UTC приёма + исходное); калибровка смещения часов
  регистратора при подключении клипов.
- Контейнеры: healthcheck + `restart: always`; watchdog «10 минут без сигналов в рабочие
  часы → тревога админу в отдельный TG-канал»; внешний пинг (UptimeRobot).
- Бэкапы: ночной дамп БД, конфиги в git, протестированный restore-скрипт.

## 10. Тестирование

- **Golden-тесты детекторов**: записанные треки с известными нарушениями; «найди ровно
  эти, не найди лишних». Ни одно изменение детектора не мерджится без прогона набора.
- **Vision**: размеченный набор кадров из первых записей парка; порог не деплоится,
  если precision на наборе упал.
- **E2E**: replay проигрывает сутки за минуты → проверка ленты, уведомлений, отчёта.
- **CI**: GitHub Actions на каждый коммит.

## 11. Безопасность и данные

- HTTPS всюду (Caddy, автосертификаты); роли; лог просмотров клипов («кто смотрел»).
- Клипы только по событиям (без сплошного архива); ретеншн 30–90 дней, автоудаление.
- Сервер физически в Казахстане (VPS РК или машина парка) — требования закона РК
  «О персональных данных» подтвердить у юриста (открытый пункт).
- Секреты в `.env`, вне git.

## 12. Эксплуатация

- Пилот: один VPS (4–8 vCPU, без GPU). Масштаб: GPU-сервер или ночной батч на ПК с видеокартой.
- Три команды: `make up` / `make deploy` (pull + rebuild + миграции) / `make backup`;
  к каждой — runbook для оператора без опыта разработки.
- Логи структурные; просмотр — админ-страница панели.

## 13. Вне объёма v1

Салонные события (падение/драка), мобильное приложение, микросервисы/Kafka/k8s,
edge-блоки в автобусах, собственный DMS-детектор при работающем штатном DDAW,
n8n (до появления реальных интеграционных задач).

## 14. Открытые вопросы и риски

1. Вендор MDVR/видеоплатформы → определяет адаптер `clips/`.
2. Тариф Link+ парка, доступ к API и частота обновления телеметрии.
3. Ночуют ли все борта в одном депо, есть ли Wi-Fi (нужно для батч-fallback видео).
4. Юридические требования к видеоданным работников в РК (юрист).
5. Ракурс штатной камеры водителя — go/no-go для vision по первым записям.
6. Точность vision в ночных/ИК-условиях — оценить на реальных кадрах до обещаний парку.

## 15. Критерии успеха пилота

1. Лента работает на replay-данных — демо не зависит от парка.
2. Затем на живых данных одного борта: ≥ 70% подтверждений по телеметрическим типам,
   ≤ 30 событий/день после недели тюнинга, разбор ≤ 30 с/событие.
3. Недельный отчёт, который директор СБ готов показать руководству парка.
